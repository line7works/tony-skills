# E17 fix round 1: one suite run per review, one lens per reviewer (build plan, 2026-10-24)

Intent: signoff-v2's review of the E17 canary took about 10 hours. Two station faults made it that long. Every reviewer ran the repository's full suite on its own (about 3 hours each) beside the session's own run of it (canary finding C-12). And the five DEEP lenses got byte-identical mandates, each listing all five lenses, so the run paid for five full reviews instead of one review split five ways (C-7). This plan fixes those two, and nothing else.

Source: the E17 canary's findings C-12 and C-7, recorded in the control room's notes on 2026-10-22, and the canary signoff's run (`astra-outputs/e17/canary/signoff-run` and `signoff-readers-extra` in the clerk repo). The owner asked for the speed-up ("Running one at a time took almost 12 hours. We need to speed that up.") and gave the go for this plan ("Go").

Constraints:

- The repo is public: no secrets, personal paths, mail addresses, key-shaped strings or em dashes in any file. One exception: the two slice headings' separator, which signoff-v2's ledger requires (`ledger.py:29`; the owner: "Em dash ok"). `mandate_text` already holds two em dashes (`signoff.py:526` and `:541`); new code and text add none.
- Never rewrite stored history: earlier verdict docs, records and run directories stay as they are.
- The independence rules, the evidence rules, the anti-rubber-stamp rule and the recording transaction do not change. A clean review still lists its executed checks (Step 4, rule 3).
- One test module runs as `cd plugins/signoff-v2/skills/signoff-v2/scripts/tests && uv run --python /usr/bin/python3 --with jsonschema==4.25.1 python3 -m unittest discover -s . -p '<module>.py'`; an adapter's module the same way from `plugins/signoff-v2/skills/signoff-v2/adapters/<harness>/tests`.
- The full suites are the same commands with `-p 'test_*.py'`, run from `scripts/tests`, `adapters/claude-code/tests` and `adapters/codex/tests`.
- No push, no PR, no merge: the owner's word only.

## Slice A — one full suite run per review

Status: not started

Requirements:

- The reviewer's mandate (`mandate_text` in `plugins/signoff-v2/skills/signoff-v2/scripts/signoff.py`) tells each reviewer that the reviewing session runs the repository's full test command once for this review, and that the reviewer does not run the full suite or any long-running sweep itself. A reviewer runs the narrowest command that proves or refutes its finding: one test module, one test, or a probe it writes in its own scratch directory. It lists each one under its executed checks as it does today.

## Slice B — one lens per reviewer

Status: not started

Requirements:

- One table in `signoff.py` holds what each lens looks for, for all seven lens names, in these words:
  - `spec`: does the built thing match the doc? Silently skipped requirements, quietly narrowed scope, stubs presented as finished. Walk the slice's acceptance criteria one by one and check files changed outside its Footprint.
  - `correctness`: bugs, unhandled edge cases, error paths that swallow failures, state that can desync.
  - `seams`: integration with what already shipped. Regressions in prior slices, broken assumptions at the boundary, migrations that do not run twice.
  - `security`: authz, injection, secrets, trust boundaries.
  - `tests`: do the tests assert real behavior, or do they pass vacuously?
  - `accessibility`: screen-reader and keyboard paths, contrast, focus order, labels.
  - `data-safety`: migrations, backups, destructive writes, data at rest.
- `request` writes one mandate per lens in the review's lens set at `readers/mandate-<lens>.md`, beside the existing `readers/mandate.md`, for every lens whose name matches `^[a-z][a-z0-9-]*$`. In each, the lens section and its table line name only its own lens; one sentence lists the review's other lenses as covered by sibling reviewers. A reviewer still reports anything it finds outside its lens; it does not go looking there.
- Every section of a lens's mandate other than the lens section is the same as in `readers/mandate.md`: the packet, what is not evidence, the finding shape, read-only, the sheet, and Slice A's suite rule.
- LIGHT's one fused lens (`spec + correctness`) writes no per-lens file: its reviewer is called with no `--lens` and keeps `readers/mandate.md`, which already names it. A LIGHT run's `request.json` carries an empty map, so any `--lens` on a LIGHT run is refused.
- `request.json` carries a map from each lens to its mandate path (empty for LIGHT). Each adapter's request mode (`adapters/claude-code/reviewer.py`, `adapters/codex/reviewer.py`):
  - binds each `--lens` block's `mandate` to that lens's own mandate, and drops the map from every block;
  - refuses a `--lens` that is not in the map;
  - takes `--lens <lens>-r<N>` (N of 2 or more) as a re-send of `<lens>` (Step 3's one re-send, a fresh call id in the shape `<run_id>-review-<lens>-r<N>`), bound to `<lens>`'s mandate;
  - with no `--lens`, binds the single block to `readers/mandate.md`, as today;
  - on a `request.json` with no map (a run written before this change), behaves exactly as today.
- The Codex adapter's mandate check (`adapters/codex/reviewer.py:247`) accepts `readers/mandate.md` or one of this run's own lens mandates, and nothing else.
- SKILL.md Step 3 and the contract say each lens's reviewer receives its own lens's mandate. The contract's complete write list (section 8, item 1, `:321`) and its run-directory table's `readers/` row (`:618`) gain the per-lens files. Both adapters' `profile.md` request-mode text (`adapters/claude-code/profile.md:92`, `adapters/codex/profile.md:82`) says each lens's reviewer receives its own lens's mandate.

Checks:

- A new core test module, `test_e17_lens_mandates`, red before the change: a DEEP run whose sheet turns `accessibility` and `data-safety` off writes five lens mandates (with no sheet, seven), whose lens sections differ pairwise, each lens section and table line naming only its own lens, and whose other sections equal `readers/mandate.md`'s; a LIGHT run writes no per-lens file and an empty map.
- A new test module, `test_e17_lens_mandates`, in each adapter's tests, red before the change: request mode with five `--lens` flags gives five blocks, each bound to its own lens's mandate and carrying no map; an unknown lens is refused; any `--lens` on a LIGHT run's empty map is refused; `--lens spec-r2` binds spec's mandate; no `--lens` still binds `readers/mandate.md`; a `request.json` with no map behaves as today.
- The full signoff-v2 core suite and both adapters' full suites pass (the commands in Constraints).
