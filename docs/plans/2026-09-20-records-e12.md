## 6. The event log

### 6.1 Addresses (specification and history separately addressable)

For a ledger document at workspace-relative path `D`, the log lives at
`docs/records/<slug>.events.jsonl`, where `<slug>` is `D` with its `.md` suffix removed and
every `/` replaced by `__` (`docs/plans/2026-09-06-readers.md` gives
`docs__plans__2026-09-06-readers`). Two addresses, returned by every reader response:

- `spec`: `{"doc": D, "slice": "<name>" | null}`. The build doc and, where one applies, the
  slice heading. The specification is never copied into the log.
- `history`: `{"log": "<log path>", "seq": n}`. One event.

The log is a tracked file. It is UTF-8, one canonical JSON object per line (the pilot's
`canonical_json`: sorted keys, no insignificant whitespace, `ensure_ascii` false), LF line
endings, one trailing newline.

### 6.2 The event

Common fields on every event:

| Field | Meaning |
|---|---|
| `v` | event schema version, `1` |
| `seq` | 0-based position in the log; equals the line index |
| `prev` | SHA-256 (hex) of the previous line's bytes without its newline; 64 zeros at `seq` 0 |
| `kind` | one of the kinds below |
| `at` | `YYYY-MM-DD` for a legacy event (all a legacy record carries); RFC 3339 UTC for a native one |
| `ledger_doc` | `D` |
| `actor` | `{"station", "run_id" \| null, "harness" \| null}`; the importer is station `records-import` |
| `origin` | `{"kind": "native"}` or `{"kind": "legacy", "doc", "doc_sha256", "line", "raw", "heading_line", "recorded_commit", "commit_named"}` |
| `source` | section 8 |

Kinds and their own fields:

| Kind | Fields | State effect |
|---|---|---|
| `log_opened` | `interface_version`, `component_version` | none; always `seq` 0 |
| `finding_raised` | `finding`, `slice`, `severity`, `location`, `claim` \| null, `scenario` \| null, `raised_by` | the finding exists and is open |
| `disposition` | `finding`, `disposition` (`fixed` \| `not_fixed`), `how`, `verified_source`, `join_basis` | `fixed` clears it (section 8); `not_fixed` leaves it open |
| `defect_raised` | as `finding_raised` plus `caused_by` (a finding ID or null) | a new finding, open, charged to `slice` |
| `waived` | `finding`, `severity`, `words` \| null, `grant_date`, `verified_source`, `join_basis` (optional) | clears it |
| `reopened` | `finding`, `words` \| null, `grant_date`, `join_basis` (optional) | opens it |
| `card_observed` | `slice`, `value` | none; what a `Status:` line said when an import read it |
| `card_set` | `slice`, `before`, `after` | none on findings; records a native card move |
| `legacy_unparsed` | `reason` | none; a line under a record heading that fits no shape and bears no state |
| `import_started` / `import_finished` | `doc_sha256`, `lines_read`, counts | none; brackets one import pass |
| `resolution_applied` | `line`, `answer`, `answered_by`, `answered_on` | none of its own; the event it enables follows it |

`location` is an object: `raw` (the field exactly as written), `file`, `line`, `line_end`
(null unless a range), `tag` (the glued parenthetical, null when none), `more` (further
locations named in the same field, each with the same four keys), and `resolved` (false when
the field names no `file:line`, in which case `file` and `line` are null and `raw` is all
there is). `event.schema.json` encodes which fields each kind requires and forbids.

## 7. Finding identity

A finding ID is `f1:` followed by the first 20 hex characters of the SHA-256 of the
canonical JSON of `[ledger_doc, slice, location_key, claim_key]`, where:

- `slice` is the canonical slice name, or `"none"`.
- `location_key` is `location.raw` with backticks removed, a glued parenthetical tag
  removed (E8-22: the tag is not part of the join key), internal whitespace collapsed, and
  case kept.
- `claim_key` is the claim with parentheses that wrap the whole field removed (E8-A28) and
  internal whitespace collapsed; when the record has no claim it is the scenario the same
  way; when it has neither it is the empty string.

The ID is computed once, when the finding is raised, and stored in the event. It is never
recomputed from a later record: a recheck, waiver, or reopening refers to the stored ID,
found by the join of section 11.4 (legacy) or supplied by the station (native). The prefix is
the version: a future scheme is `f2:` and both can sit in one log.

Identity is ambiguous, and the operation stops with an explanation (exit 5, section 12.3),
when: two `finding_raised` candidates in one document would receive the same ID (the pilot's
"two review findings with the same location and claim in one block", widened to the
document); a native writer supplies an ID the log does not hold; a native writer raises a
finding whose computed ID the log already holds (it must send a `reopened` or a new claim,
never a silent second raise).

## 8. Source identifiers and clearing

8.1. A known source is the pilot's six-field identity, unchanged (pilot contract section 6;
`identity.py`'s `identity_of`): `commit`, `dirty`, `tracked_diff_sha256`, `untracked`,
`untracked_sha256`, `submodules`. The events' `source` is
`{"known": true, "identity": {…six fields…}}` or `{"known": false}`. A workspace with an
initialized submodule is refused the way the pilot refuses it.

8.2. The identity a native event carries is computed with the log file and the other files
under `docs/records/` excluded from the dirty check, the tracked diff, and the untracked
list, so that appending to the log does not change the identity of the source the log
describes. The exclusion list is fixed (`docs/records/`), recorded in `interface.md`, and
tested.

8.3. **A record cannot clear findings against a different source revision.** `append`
refuses a `disposition` with `disposition: "fixed"`, and a `waived`, unless all of these
hold: the event carries `verified_source` with `known: true`; the identity the component
computes in the workspace at append time equals it field for field; the finding it names is
open in the state derived from the log's current head. A mismatch is exit 6
(`stale_source`), with both identities in the response and nothing written. The importer is
the one writer allowed to append a clear with `known: false`, and only with
`origin.kind: "legacy"` (owner ruling O4).

8.4. Derived state reports, for every cleared finding, the source it was cleared against.
`state --at-source <identity.json>` adds, per cleared finding, `cleared_at_this_source`:
true only when the clear's `verified_source.identity.commit` equals the given commit and the
clear was bound. It changes no state; it lets a station see which clears were verified on the
revision in front of it.

## 9. Derived state

9.1. State is a pure function of the log's bytes: the same log gives the same state object,
byte for byte, on any machine (`state.schema.json`; canonical JSON). Nothing is cached on
disk in E12.

9.2. Per finding: `id`, `slice`, `severity`, `location`, `claim`, `scenario`, `status`
(`open` | `fixed` | `waived`), `cleared_unbound` (true when the deciding clear has
`known: false`), `join_basis` of the deciding event, `raised` and `decided` as history
addresses, and `events` (every `seq` that names it). The deciding event is the last event in
`seq` order that names the finding among `disposition`, `waived`, `reopened`; none means
open. This is Appendix A's open filter with the finding ID as the join key.

9.3. Per slice: `open` by severity, `card_derived` by Appendix A's mapping (any BLOCKER open
gives `rejected`; else any MAJOR open gives `signed off with conditions`; else `signed off`;
a slice last observed or set at `built` keeps `built`; `docs/punch-list.md` has no card),
`card_observed` (the last `card_observed` or `card_set` value), and `card_drift` (true when
both exist and differ). A `card_observed` event keeps the `Status:` text exactly as written
in `value` and adds `card`: that text when it is one of the pilot's six card values, else
`none` (the pilot's rule; real cards read `built (2026-09-15; awaiting signoff)` or
`superseded by Slice L …`, and the component does not guess at them). The component reports drift; it never corrects a card in E12.

9.4. `render` produces, from a run's events, the exact Appendix A text the pilot writes for
the same facts: the block heading, the recheck and defect lines, the waiver and reopening
lines. The parity suite holds it to the pilot's bytes on the E7 fixtures. Nothing in E12
writes that text into a document; E13 decides where a station puts it.

## 10. Conflicting writes

- **The chain.** `verify` walks the log: every line parses and validates; `seq` equals the
  line index; every `prev` equals the hash of the line before. Any break is exit 7
  (`conflict`) naming the first bad line. A git merge that joined two tails is caught here:
  the second tail's first `prev` names a line that is no longer its predecessor.
- **Optimistic append.** `append` takes `--expect-head <sha256>` (the hash of the last line
  the caller read, or 64 zeros for a log that does not exist yet). When the head on disk
  differs, nothing is written: exit 7, with the expected and the actual head. A station
  re-reads and decides; the component never merges for it.
- **The lock.** `append` and `import-legacy` hold `<log>.lock`, created with exclusive
  creation (`O_CREAT | O_EXCL`), holding the pid and the start time, removed on exit. A lock
  that exists is exit 7 with its contents; `--break-lock` removes a lock only when its pid is
  not alive and says so in the response. No waiting, no retry loop.
- **Batches are atomic.** `append` takes one or more events from a file and writes all or
  none; `seq` and `prev` are assigned by the component, never by the caller.

## 11. The legacy importer

### 11.1 The measured corpus (2026-09-20, read-only, the pilot's own reader)

Record headings of Appendix A were searched across the owner's working repositories, with
worktree copies and archived repositories left out. 72 documents in 19 repositories carry
them: 55 ledger documents (build docs and punch lists) and 17 verdict docs holding block
copies. In the 55: about 2,640 review-finding lines, 780 recheck lines that state a
disposition, 140 fix-introduced defect lines, and a handful of waiver and reopening lines.

The pilot's strict reader (`ledger.parse_document`) reads 1,189 of the 3,839 record lines in
the 72 documents as records and calls 2,650 ambiguous. Why, by family (counts from the 72):

| Family | Lines | Shape |
|---|---|---|
| L1 | 813 | one location wrapped in backticks, otherwise `file:line` |
| L2 | 507 | one location with a line range, `file:N-N` |
| L3 | 318 | no line number: a file, a section, or a described place |
| L4 | 303 | several locations in one field |
| L6 | 98 | one location followed by a parenthetical tag, with backticks or a range |
| L5 | 40 | other location forms (a bare `:N` continuation, a path outside the repo, a note) |
| F1 | 368 | recheck line whose disposition and how-verified share one field (`fixed — how`) |
| F2 | 64 | review finding with 3, 6, 7, or 8 fields |
| F3 | 40 | defect line with an extra or missing field, or without the `broke: claim — scenario` form |
| F4 | 43 | recheck line of another pattern: 3, 4, or 6 fields, or a fourth field that is not a disposition |
| S1 | 29 | first field is not a severity (`QUESTION` and similar) |
| D1 | 27 | two findings with one location and claim in one block |

Joining the 780 disposition lines back to findings inside their own document, after the
normalization of section 11.3: 22 percent match exactly one finding on location plus claim;
47 percent match exactly one finding on location alone, the claim having been reworded;
less than 1 percent match on claim alone; 18 percent name a location several findings share
with no claim match; 13 percent match nothing in the document. Almost none names the commit
it verified.

What this means for E12: the strict reader is right for what the pilot writes and wrong as
an importer; the importer needs its own tolerant reader, a defined join, and a way to take
an answer for the third of clears that no rule can place. The control room keeps the survey
scripts and their per-document output in the audit packet, outside this repository.

### 11.2 What the importer is

`records.py import-legacy --workspace W --doc D [--resolutions R] [--dry-run]` reads one
ledger document and writes (or, under `--dry-run`, only reports) the events that represent
its records, in file order, into the document's log. It never writes to `D`, to a verdict
doc, or to anything outside `docs/records/`. It runs no git command that changes state.

### 11.3 The tolerant reader

It accepts everything the strict reader accepts, with the same result, and in addition:

- a location wrapped in backticks (L1); a line range (L2: `line` and `line_end`); a glued
  parenthetical tag after any of these (L6); several locations separated by `,`, `;`,
  ` and `, or ` + `, the first becoming the location and the rest `more` (L4); a bare `:N`
  in `more` inheriting the first location's file; a field with no `file:line` at all (L3,
  L5) kept as `raw` with `resolved: false`;
- a recheck line whose fourth field begins with `fixed` or `not fixed` followed by a dash
  (em, en, or hyphen) and text (F1): the word is the disposition and the text is `how`;
- a review finding with more than five fields (F2): fields 1 to 4 are severity, location,
  claim, scenario; the last field is `raised_by`; anything between joins the scenario with
  the separator kept; with three fields the third is the scenario and the claim is null (the
  pilot's legacy claim-less shape);
- a defect line in either legacy form (`broke: …` with or without the dash, or a field
  reading `fix-introduced`), with the text after the marker as the claim.

A line under a record heading that still fits nothing, or whose first field is not a
severity (S1), becomes `legacy_unparsed` with its raw text. It bears no state and blocks
nothing. The fence rule (E8-20), the heading rule, and the slice rule are the strict
reader's.

### 11.4 The join (which finding a clear belongs to)

For a recheck, waiver, or reopening line, in this order, inside the one document:

1. location key and claim key equal exactly one finding: `join_basis: "exact"`;
2. no claim in the line (`()` or absent) and the location key is held by exactly one
   finding: `"location_only_no_claim"` (the pilot's rule);
3. the location key is held by exactly one finding, and that finding's slice is one of the
   heading's slices: `"location_only"` (owner ruling O3);
4. anything else is ambiguous.

### 11.5 Ambiguity stops the document

When any state-bearing line is ambiguous (rule 4 above, or the identity cases of section 7),
the import of that document writes nothing and exits 5 with a report listing every such
line: its number, its raw text, the reason, and the candidate finding IDs with their lines.
The owner, or a session on the owner's word, answers in a resolutions file
(`resolutions.schema.json`): per line, either `{"line": n, "finding": "<id>"}`,
`{"line": n, "new_finding": true}`, or `{"line": n, "skip": true, "why": "…"}`, plus
`answered_by` and `answered_on`. A resolution that names a line whose raw text has changed,
or a finding the document does not raise, is rejected. Each answer used is recorded as a
`resolution_applied` event before the event it enables, so the log shows which joins a
person decided. `skip` records the line as `legacy_unparsed` with the reason.

### 11.6 Verdict docs are mirrors

The importer does not import a verdict doc. `records.py mirrors --workspace W --doc D` finds
the verdict docs the pilot's glob associates with `D`'s slices, reads their blocks with the
tolerant reader, and reports each block as `same`, `differs`, or `absent` against the ledger
document, plus `only_in_mirror` for records a verdict doc holds that the ledger document
does not (a demonstration run recorded only there is a real case). A difference is reported,
never repaired, never imported, and never blocks an import. Measured in this repository:
the recheck lines of the readers verdict docs are byte-identical to the build doc's, while
the signoff finding lines of five of them are worded differently from the build doc's
`review:` blocks, which is why a mirror is never a second source.

### 11.7 Without changing history

- The legacy document's SHA-256 before and after an import is equal, and the test suite
  checks it on every fixture, along with `git status --porcelain` showing only the log.
- A second import of an unchanged document appends nothing (`imported: 0`).
- A second import of a document that has only grown at its tail (the v1 stations are still
  in use) appends only the new records. The importer proves "only grown" by re-reading the
  previously imported lines and matching each `origin.raw` and `origin.line`.
- A document whose previously imported lines changed or moved is exit 7 (`conflict`) naming
  the first such line; nothing is written. The owner decides what happened.
- `origin.recorded_commit` is the commit `git blame` (read-only) gives for the line when the
  document is tracked, else null. It says when the line was written down. It is not the
  source the line verified, and nothing treats it as one.
- An imported event's `at` is the block heading's date (or the grant's date on a waiver or
  reopening line); `source` is `{"known": false}` unless the line names a full 40-hex commit,
  in which case the importer records it under `origin.commit_named` and still leaves
  `known: false` (a bare commit is not the six-field identity).

### 11.8 What E12 does not do

E12 ships the importer, its fixtures, and `survey` (`records.py survey --workspace W`: per
document, the counts by record kind, by join basis, and the lines that would stop an
import; read-only). Running `import-legacy` over the owner's repositories writes new tracked
files into each of them and needs answers to several hundred ambiguous lines. That is a
separate job on the owner's word, after E12 closes, one repository at a time.

## 12. The interface

### 12.1 Reaching the component

A station resolves the component root in this order and uses the first that holds
`scripts/records.py`: the `--records-root` argument; the `RECORDS_ROOT` environment
variable; `<station plugin root>/../records`; nothing found is exit 3 with
`missing dependency: records component (looked in: …)`. Slice 3 proves each of the three on a
checkout and records, for Claude Code and for Codex, where an installed plugin's sibling
actually sits, by installing into an isolated home (never the live one) the way
`plugins/recheck-v2/setups/` does. If a harness does not keep siblings beside each other,
the builder reports it and the control room rules; the builder does not invent a fourth
lookup.

### 12.2 Commands

Every command: `--help` with arguments, defaults, an example, and side effects; JSON on
stdout and nothing else; diagnostics on stderr; safe to run from any working directory. Every
response carries `interface_version`, `component_version`, and, where a log is involved,
`log`, `head` (the hash of the last line), and `events` (the count).

| Command | Does | Writes |
|---|---|---|
| `verify --workspace W --doc D` | section 10's chain and schema walk | nothing |
| `state --workspace W --doc D [--at-source F] [--slice S]` | section 9 | nothing |
| `events --workspace W --doc D [--finding ID] [--kind K] [--from N]` | the events, filtered, each with its history address | nothing |
| `identity --workspace W` | section 8.2's identity | nothing |
| `append --workspace W --doc D --events FILE --expect-head H [--break-lock]` | sections 7, 8.3, 10; validates every event, assigns `seq` and `prev` | the log |
| `render --workspace W --doc D --run-id R` | section 9.4 | nothing |
| `import-legacy --workspace W --doc D [--resolutions R] [--dry-run]` | section 11 | the log |
| `mirrors --workspace W --doc D` | section 11.6 | nothing |
| `survey --workspace W` | section 11.8 | nothing |
| `component-identity` | `{name, version, commit, content_sha256}` of the component root | nothing |

### 12.3 Exit codes

0 success; 1 anything else; 2 usage; 3 missing dependency; 4 an input, an event, or a log
line failed validation; 5 ambiguous identity (the response explains every case); 6
`stale_source`; 7 `conflict` (chain break, head mismatch, lock held, changed legacy
history). 0 to 4 are the A7a meanings; 5 to 7 are this component's and are listed in
`interface.md` as part of interface version 1.
