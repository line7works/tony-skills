# E18 fix round 1: signoff-v2 records a kept note honestly (build plan, 2026-10-27)

Intent: the first live one-command run (ship run ship-a-20261027-fb9c, on `docs/plans/2026-10-26-e18-live-run.md`) built its slice and its fresh signoff session signed it off, but the run stopped `visit-unfinished` on two signoff-v2 defects. This round fixes those two, bumps the two plugins whose files changed since the reinstall, and nothing else. Then a second live run.

Source: the live run's report and signoff-v2 SKILL NOTEs from E18 Slice D's two signoff runs (PR #120). The owner's word: "fix round" (2026-10-27).

The defects:

1. A kept note breaks the result. `signoff_core/answer.py` `adjudicate` copies each `notes_kept` entry into the result's `notes` as the reviewer wrote it. `answer.schema.json` lets a kept note's `severity` be null; `result.schema.json` gives `notes` the `finding` shape, whose `severity` must be BLOCKER, MAJOR or MINOR. So `record` writes a result its own schema refuses and exits 4. And the check that runs before any project-record write (`signoff.py` `cmd_record`, Astra's F16) runs only the semantic validator, not the schema, so the verdict doc, the records events and the card all land first: the records say signed off while the run says stopped.
2. A late quotation looks withheld. `signoff.py` `provenance_of` reads the delivered packet through `signoff_core/packet.py` `read_text_or_none`, which stops at `MAX_DELIVERED_BYTES` (512 KiB, a per-file delivery cap). A packet larger than that (Slice D's was 862 KB and 949 KB) is cut, so a reviewer quoting the back of the packet is refused on independence as if the words came only from the builder's withheld notes.

## Slice A - a kept note never breaks the result

Status: signed off

Requirements:

- A result's `notes` entry may carry a null `severity`: `result.schema.json` gives `notes` its own shape, which takes every value `answer.schema.json` allows on a kept note (requirement 4), a null `severity` included. `findings` (what was raised) keeps a required severity. A kept note's other fields are recorded as the reviewer wrote them; the answer is never edited.
- The check before any project-record write runs the result schema as well as the semantic validator on the proposed completion. A proposed result that fails either stops the run with nothing recorded (no verdict doc, no records event, no card move), naming the schema error.
- The chat block and any other rendering of a note with a null severity print it without a severity rather than failing or printing "None".
- Added on the owner's ruling after the first signoff run ("fold and fix"): every value `answer.schema.json` allows on a kept note (`$defs/reported`: any field null or any string, a severity outside BLOCKER, MAJOR and MINOR included) and on a reviewer's check (`checks_executed`, an `output` null or missing included) is recorded in the result as written, so no answer the answer schema accepts makes `record` refuse or exit 4 on those fields.
- A stop from the pre-write check writes a result that passes the result schema whatever the answer carried, and keeps the raised findings and the notes in that result and its chat block, so a raised finding never vanishes from a stopped run.
- No other change.

## Discovered

### 2026-10-27 - Slice A (build run build-a-20261027-fr1a)

- `answer.schema.json` lets every field of a kept note be null or any string (`$defs/reported`), while the result's note shape still requires a non-empty location, claim and scenario and an `evidence_kind` of executed, read or reasoned, and a severity spelled other than BLOCKER, MAJOR, MINOR or null (say `minor` or `NOTE`) is refused too. Such a note now stops `record` with nothing written instead of landing the records and exiting 4, but the review is still lost to the run; logged, not built (`answer.schema.json` is outside this slice).
- No other reader of a note's severity was found: the verdict doc and the records events carry raised findings only; ship-v2's `stations.outcome` and `visit._named` read the signoff result's `findings` and never its `notes`; signoff-v2's `evals/seeded-cases/observe.py` reads note locations only.

### 2026-10-27 - Slice B (build run build-b-20261027-fr1b)

- `read_text_or_none` with the cap reads `MAX_DELIVERED_BYTES + 1` bytes and decodes them whole, so a delivered file over 512 KiB whose byte 524289 falls inside a multibyte character is withheld as "binary or not UTF-8 text" instead of delivered truncated (probed: 524288 ASCII bytes, then an e-acute, returns None). Packet assembly and truncation are outside Slice B; logged, not built.
- `withheld_text` reads the ledger doc through the same capped reader, so in a ledger doc over 512 KiB the withheld lines past the cap never reach the independence check, and a quotation from them is not refused (found by reading `signoff.py` `withheld_text`, not exercised). Outside Slice B ("the withheld-text readers other than the delivered material"); logged, not built.
