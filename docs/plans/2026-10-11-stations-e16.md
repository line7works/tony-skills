## 1. What E16 delivers

Plan text, verbatim. **E16. Rebuild sunrise and sunset around explicit operations.** **Artifact:**
Shared lifecycle code, provider integrations, preview manifests, templates, and restoration
instructions. **Done when:** Disposable-project checks demonstrate correct vault/machine
preflight, staged-document adoption, credential-safe execution, declared Git behavior, resumable
partial failure, and restoration. Sunset's default preserves records without depending on a Trash
expiration window. **Runs:** X + S; C handles Claude-owned integration checks; O handles actions
requiring account/UI authority; R reviews. **Dependencies:** E12, E15. **Owner gate:** D6 for any
broader bootstrap Git exception. Real service operations require the authorization named in their
preview.

The plan, beside it: "The sound `.env.example` checks and database backup requirements remain. The
script extraction must test tracing and error output, not merely move the commands."

Plan amendment A8: "The lifecycle scripts follow the A7a helper interface, and the script
extraction tests the tracing and error-output paths for credential exposure. D6 as ruled: sunrise
may push the initial scaffold to `main` of a brand-new repo." Decision register 13 (D6), the owner:
"Sunrise push to main is fine because it'll be spinning up a brand new repo and everything, and
pushing to main won't hurt anything."

**Runs, read under the owner's crew ruling of 2026-10-11 (section 5, R2).** His ruling replaces
the plan's "X + S" line for this step: one Opus 5.5 builder at high per slice; the outside reviewer
(Astra, GPT-6, through `codex exec` on a sealed copy) at low is the checker of every hand-back; a
script with no model runs the suites. "C handles Claude-owned integration checks" is read as the
Claude adapter's own checks (section 6, E16-14). "O handles actions requiring account/UI authority"
is read as the owner: an operation only his account or his click can perform is shown to him with
the exact step and waits for him (E16-4, the `owner` class).

In plain words: sunrise starts a project on every layer it needs and sunset retires one on every
layer it lives on. v1 does both as prose a model follows, 541 and 316 lines. E16 rebuilds them so
that every change to the machine or to an outside service is an **operation**: a small record with
a name, a target, a check that tells whether it is already done, the exact effect, and the way
back. Five things get built.

1. **The lifecycle frame (slice 1).** The operation record, the plan of operations (the manifest),
   the preview rendered from it, the run journal, resume, the credential guard, the provider
   interface with fake providers, and the vault and machine gate.
2. **Sunrise, the local half (slice 2).** The new repo and its doc kit, staged-document adoption,
   the vault entry, memory and the terminal shortcut, as operations.
3. **The providers (slice 3).** GitHub, Vercel, Supabase through the Vercel Marketplace, and the
   provider-blind database backup, each behind the frame's interface, each with a fake.
4. **Sunset and restore (slice 4).** Retirement as operations whose default leans on no expiry
   window, and a restore manifest written at sunset so the way back is executable (P16).
5. **The join (slice 5).** One throwaway project taken through sunrise, sunset and restore on the
   real services with the owner present (P12), install proofs on both harnesses, marketplace
   entries, README counts, guide findings, the full outside review.

Out of scope: Notion on any layer (R3); any provider outside R4; cutover or retirement of the v1
`sun` plugin (P14; E17 to E19); any change to `plugins/records/`, `plugins/readers/` or the ten v2
cores (E16-2); the carried E15 punch-list items (R6, E18's pre-release round); the OpenCode
adapters; a third harness.

**Measured in v1 on `5cf37d5`, for the picks.** Notion is named on 26 lines of sunrise and 15 of
sunset. Every one of the 7 lines of sunset that names the Trash names Notion's (the board is
"moved to trash, restorable ~30 days"); with Notion out, no v1 step leans on a Trash window, and
what remains of that class is each provider's own retention clock on a paused resource (section
16, design page 3). Neon is named on 4 lines of each skill. "npm publish" is a column of sunrise's
project-type table and no phase publishes anything. v1 passes the database connection string to
`pg_dump` as an argument and the Vercel token to `curl` in a header argument: both are visible in
the process table while the command runs (section 16, design page 2).

## 3. Boundaries every slice keeps

- One writer per worktree. A builder writes only under the folders its slice names (section 13) and
  the scratch directory it is given. Never `plugins/records/`, `plugins/readers/`, any of the ten
  v2 cores, any v1 plugin folder (`plugins/sun/` included), `.claude-plugin/marketplace.json` (the
  control room adds entries at close), `docs/feedback.md` or `docs/ideas.md`.
- A builder never runs `git add`, `commit`, `stash`, `checkout`, `reset`, `merge`, `worktree`,
  `branch`, or any git command that changes a worktree, its index or its branches. `status`, `log`,
  `diff`, `rev-parse`, `show`, `archive` to a temporary directory are fine. Git commands inside a
  test's own temporary repository are the test's. The control room checks every round and makes
  every commit.
- **No real service in slices 1 to 4.** No builder, test, proof or reviewer run calls a real `gh`,
  `vercel`, `supabase`, `psql` or `pg_dump` against an account, opens a real credentials store, or
  touches the real vault, the real memory stores, the real shortcut file, a real crontab or a real
  LaunchAgents folder. Every provider is its fake (E16-8); every machine location is a path under
  the test's temporary directory, reached through the one place the core resolves it (E16-12).
  The only real-service run of this step is slice 5, with the owner present.
- Runtime floor: `/usr/bin/python3` 3.9.6 and git 2.50.1. Python 3.9 syntax. Standard library
  only, with the one declared exception, `jsonschema==4.25.1` through `uv run` (PEP 723); a script
  started without it exits 3 with a plain message. `--help` and argument checks work without it.
- No network in any test. No MCP tool. No model call inside any script. A core's script never
  launches a harness and never invokes another skill.
- Tests build their fixtures in a temporary directory and clean up (`PYTHONDONTWRITEBYTECODE=1`; no
  `__pycache__` left). Install probes run only in isolated homes. Suites are written so their
  modules run side by side from the first slice (P4).
- The repository is public. Fixtures are synthetic: no text copied from another repository, no
  personal, legal or financial content, no personal paths, no machine names, no account names, no
  key-shaped strings (a planted test secret is a marked canary built at run time, never a literal
  in a committed file that a scanner would read as a key).
- Test first for every behavior a check of section 12 or a required test names: the failing output
  is recorded before the code that makes it pass.
- No em dashes in anything written for this step, except inside a v1 form copied byte for byte
  where the form is ruled load-bearing (E16-13 names them).

## 6. Rulings of this contract

- **E16-1, behavior is kept, the mechanics move.** Sunrise keeps: the vault gate first; never
  clobber; preview before executing and an explicit go; ask what the project is and use his words;
  layers conditional on the project type; end verified (the push landed, the clean production
  address answers 200, the pulled env file holds its keys, the kit check passes); the cross-links
  written on day one; resumable. Sunset keeps: the vault gate first; never delete; preview and an
  explicit go; ask the reason and use his words; cancel active automation; copy the project's own
  memory store only after the repo has moved; back the database up before idling it and never drop
  it; never move or archive a repo with uncommitted or unpushed work without surfacing it; the
  loose ends surfaced and never acted on. What moves is where the deterministic half lives (a
  script, not prose). What leaves is Notion (R3) and whatever the picks cut. A proposed change to
  any other decision is the owner's ruling and lands in section 18.
- **E16-2, frozen folders.** At close, `git diff --stat <branch point> -- plugins/records
  plugins/readers plugins/sun` and the same for the ten v2 core folders print nothing. A need those
  components do not meet is a numbered question and a stop on that point.
- **E16-3, the operation is the unit.** Every change a run makes outside its own run directory is
  one operation with: an id; the layer; the kind; the target; the class of authority it needs
  (E16-4); a **probe** that reads the world and answers `absent`, `ours`, `foreign` or `unknown`;
  the **effect**, as the exact commands or file writes; the **check** that proves the effect
  landed; the **way back** (an inverse operation, or the word `none` with the reason); and the
  names of the secrets it handles, never their values (E16-7). A change that is not an operation
  of the approved manifest does not happen.
- **E16-4, the preview is the manifest and the go is bound to it.** The plan of a run is an ordered
  list of operations, written to the run directory and hashed. The preview the owner reads is
  rendered from that file by script and nothing else. His go is recorded with the manifest's hash;
  execution refuses a manifest whose hash differs and any operation the manifest does not hold. A
  run that needs a new or changed operation after the go stops, renders a new preview and waits
  for a new go. Each operation carries one class: `local` (inside the project's own new or archived
  folder), `machine` (elsewhere on this machine: the vault, a memory store, the shortcut file, the
  staging folder, a crontab, a launch agent), `remote` (a write to an outside service, shown with
  the account the provider's own identity probe reports) and `owner` (an account or UI step only
  the owner can take: shown with the exact step, never attempted by the script, recorded when he
  confirms). This is the plan's "authorization named in their preview".
- **E16-5, the journal is written ahead.** Before an operation's effect, one line records the
  intent; after its check, one line records the result. The journal is append-only, lives in the
  run directory, holds no secret (E16-7) and is the record a resumed run and a restore read. Where
  the run directory lives is design page 1.
- **E16-6, resume by probing.** A rerun of an interrupted run trusts the world over the journal:
  each operation is probed again in order. `ours` with a recorded result is skipped; an intent with
  no result is decided by the probe; `foreign` stops and names what is there (never clobber);
  `unknown` stops and names the operation. No operation is applied twice. A kill at any point of
  any operation leaves a state a rerun completes or stops on plainly; the kill sweep of section 12
  proves it for every operation of every provider's fake.
- **E16-7, credentials never leave their channel.** A secret is any provider token, any database
  connection string, any value of a pulled env file and any key or certificate file. A secret
  reaches a child process only through that child's environment or through a file the child reads
  itself. It is never an argument of any command, never a byte of the manifest, the preview, the
  journal, a trace, a tombstone, a restore manifest, a result, the standard output, the standard
  error or an error message, and no script reads one aloud to the executor. Everything a child
  prints passes one redaction filter before it is stored or shown. No script and no skill text
  turns on a shell trace or a tool's verbose or trace flag on a command that handles a secret.
  The tests plant a marked canary in every source and scan every byte written, every byte printed
  and every argument the fakes record, on the success path and on every failure path (A8: "tests
  the tracing and error-output paths for credential exposure").
- **E16-8, providers sit behind one interface, each with a fake.** A provider module offers
  operations (probe, effect, check, way back) and an identity probe; the real one shells to the
  provider's own command-line tool or calls its HTTP interface in-process. A fake is a program the
  tests put first on the path: it keeps its state in a file, records every call's arguments and the
  names of the environment variables it was given, can be told to fail, to hang, to answer late and
  to echo a secret into its error text, and it can be killed mid-call. What v1 reached through a
  harness connector (the Vercel project list) the core reaches through the tool, never through a
  connector.
- **E16-9, declared git behavior.** The manifest lists every git command that changes a repository
  or a remote, and the fakes' records must equal that list. D6 is read narrowly, as ruled: sunrise
  pushes the initial scaffold to `main` of a repository this run created and whose remote holds no
  commit. There is one such push per sunrise: the operations are ordered so every edit a later
  layer makes to the working tree (the ignore-file lines a link appends, the placeholder files) is
  in the tree before it, which folds v1's second closeout push into the first (the ordering is
  design page 1's; if it cannot hold on the real services, the stop is the owner's, under D6).
  Sunset's declared remote changes are a dated tag pushed before the archive, and the archive.
  No other push, and no push to `main` of a repository that already has history.
- **E16-10, sunset never deletes and its default leans on no clock.** Every record sunset is
  responsible for reaches a place with no expiry, and is checked there, before any provider-side
  state with a retention clock is entered. A backup that cannot be verified stops the run before
  the idle step. The tombstone and the restore manifest name each clock that still runs on a
  provider's side and what is lost when it runs out.
- **E16-11, the way back is recorded when the way out is taken.** Each sunset operation records,
  at the moment it runs, what its inverse needs (the exact lines removed, the ids, the paths, the
  hashes of what moved). If P16 is ruled yes, those records are the restore manifest and `restore`
  runs it under E16-3 to E16-7; if not, the same records render the restoration instructions.
- **E16-12, the gate and the machine's facts.** The vault and machine gate is a script with v1's
  four checks; it runs before anything else, the cue included, and a failed gate creates nothing.
  Every machine location (the developer root, the archive folder, the vault, the staging folder,
  the memory stores, the shortcut file) and every account name is resolved in one module, from a
  probe or from one user-level settings file outside any repository, and is overridable for tests.
  No committed file holds a personal path or an account name.
- **E16-13, the executor decides, the script records.** A script validates inputs, runs the gate,
  probes, builds and renders the manifest, executes approved operations, writes the journal,
  renders the summary, the tombstone, the hand-off prompt and the templates. It never chooses a
  name, a project type, a shortcut or a description, never answers for the owner, and never runs a
  scaffolder that was not an operation he approved. The v1 forms the owner reads and the other
  surfaces parse (the `SUNRISE PREVIEW`, `SUNRISE COMPLETE`, `SUNSET PREVIEW` and `SUNSET COMPLETE`
  blocks, the tombstone, the two hand-off prompts, the seeded `AGENTS.md`, the one-line `CLAUDE.md`
  stub, the vault seed, the memory note, the alias line) are rendered by one module from templates
  with a round-trip test; their Notion lines leave (R3); any other change to a form is a stop.
- **E16-14, the harness seams are named.** What v1 did with a Claude Code tool or a model call
  lives in the adapter, and on Codex each is a named capability with a stated result: listing and
  cancelling scheduled routines; the two Claude memory stores; the kit check's canary line (a model
  quotes the first line of the instructions it was given). A seam that is absent on a harness is
  said so in the preview and in the summary, never passed silently.
- **E16-15, versions and interface.** The new plugin starts at `0.1.0` with `interface_version` 1
  in every CLI response. Every CLI follows the A7a helper interface (plan A8): `--help` with
  arguments, defaults, an example and side effects; JSON on standard output and nothing else;
  diagnostics on standard error; exit 0, 2, 3, 4, 10 and 1 with their A7a meanings; safe reruns;
  partial effects named in `--help`.
- **E16-16, no implicit import of v1.** A test in the new core fails on a path under `plugins/sun/`,
  on any deference to a v1 skill's text and on any subprocess whose arguments name a v1 skill. The
  shared cue assets are copied into the new plugin, not reached across.
- **E16-17, the frame freezes when slice 1 closes.** A lane that needs a frame change stops and
  asks; the control room makes the change once, in the frame's worktree, and every lane takes it.

## 16. Open questions for the design pages (decided before the builder of that slice starts)

The pages are `docs/plans/2026-10-11-stations-e16-design-1-resume.md`,
`-design-2-credentials.md` and `-design-3-restore.md`. Each ends with the questions it leaves; the
ones that are the owner's are listed here.

- **Q1, page 1.** Where a run directory lives. Sunrise starts before its repo exists and sunset
  moves its repo, so the journal cannot live in the project. Recommended: a per-user state folder
  outside every repository, resolved by E16-12's module.
- **Q2, page 1.** The one push (E16-9) needs the remote to exist, empty, while the host is linked
  and the working tree settles. If the host's link will not connect an empty repository, the
  choice is a second first-day push (a broader D6 reading, his gate) or connecting after the push.
- **Q3, page 2.** v1 reads the host's token from the tool's own credentials file when the
  environment has none. Keep that read inside the provider module (recommended, with E16-7's
  rules), or require the environment variable and stop without it.
- **Q4, page 3.** v1 writes the database backup and the copied memory store inside the moved
  repo's folder, where a later `git add` could pick them up. Keep the location and add ignore
  lines, or move both beside the repo in the archive folder (recommended; a change to where a v1
  artifact lands, so his call).
- **Q5, page 3.** A half-finished sunrise has no way back in v1; it resumes forward. Recommended:
  keep that (a sunrise is finished or resumed, and retired by sunset), and build no sunrise undo.
- **Q6, page 3.** The providers' retention clocks on a paused or idle resource are to be measured
  from the providers' own documents before slice 4's brief, not assumed.
