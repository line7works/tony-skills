## 1. What E13 delivers

Plan text, verbatim. **Artifact:** portable build and signoff cores using E12's records and
the qualified integrations. **Done when:** seeded cases prove scope adherence, honest failure
handling, correct review scope, evidence-backed initial findings, and independence. Review
covers the intended committed, changed, and untracked source set. A clean review identifies
the checks performed. Report-only behavior remains explicit. **Runs:** X authors; R
independently reviews and qualifies. **Dependencies:** E12. **Owner gate:** D4 for changes to
reviewer eligibility, reviewer counts, suite requirements, or stop rules. "Qualified v2
recheck can verify named fixes here. Initial inspection still comes from the independent
temporary reviewer until v2 signoff itself is qualified."

Handed forward by E12 (its ruling O5 and section 1): moving the qualified recheck pilot onto
the records component is the first task of E13, which re-qualifies what it changes; the Codex
per-trial session-folder lock (contract SB-14) rides with E13.

In plain words: three things get built.

1. **Recheck keeps its records in the logbook.** Today `recheck-v2` reads and writes the
   Markdown record blocks itself. After slice 1 it raises, clears, waives and reopens through
   `records.py`, and the Markdown block in the build doc is a rendering of those events.
2. **A portable build core.** One slice of a build doc, made true, inside the drawn scope,
   with plain reporting when something fails. Same procedure on every harness.
3. **A portable signoff core.** The first inspection of a built slice by someone who did not
   build it: the right source set, findings with evidence, a clean result that lists its
   checks, and findings raised into the logbook.

Out of scope: the four front stations (E14); vertical, handoff and ship (E15); lifecycle
(E16); cutover of any v1 skill (E17 to E19); running the legacy importer over the owner's
repositories (parked by the owner on 2026-09-21); any change to `plugins/records/` beyond a
defect fix the owner rules on.

## 3. Boundaries every lane keeps

- One writer per worktree. A builder writes only under the folders its slice names
  (section 13) and the scratch directory it is given. Never `plugins/records/`, never
  another lane's folder, never `.claude-plugin/marketplace.json` (the control room adds
  entries at close), never `docs/feedback.md` or `docs/ideas.md`.
- A builder never runs `git add`, `commit`, `stash`, `checkout`, `reset`, `merge`, or any
  git command that changes a worktree, its index, or its branches. `status`, `log`, `diff`,
  `rev-parse` are fine. The control room checks every round and makes every commit and every
  local merge.
- Runtime floor: `/usr/bin/python3` 3.9.6 and git 2.50.1. Python 3.9 syntax. Standard
  library only, with the one declared exception: `jsonschema` at the pin in force in
  `plugins/recheck-v2/skills/recheck-v2/scripts/recheck.py`'s PEP 723 block, through
  `uv run`. A script started without it exits 3 with the pilot's message shape. `--help` and
  argument checks work without it.
- No network. No MCP tool. No model call inside any script. A core's script never launches
  a harness; a skill body may direct the executor to summon a reviewer (signoff does, through
  `readers`), and a test never does.
- A station reaches the records component through the resolver snippet and the CLI only
  (E12 ruling O2, guide "The records assessment"). It never opens a log file, never imports
  `records_core`, never copies the component's code. It confirms `interface_version` 2 (1 until
  amendment A7 moved it; a version-1 reader asks for the compatibility response)
  through `component-identity` and stops with exit 3 and a plain message when the component
  is missing or speaks another version.
- Tests build their fixtures into a temporary directory and clean up. Nothing is written
  into a worktree by a test run (`PYTHONDONTWRITEBYTECODE=1`; no `__pycache__` left).
- Install probes run only in isolated homes, never the live `~/.claude` or `~/.codex`.
- The repository is public. Fixtures are synthetic: no text copied from another repository,
  no personal, legal, or financial content, no key-shaped strings.
- Test first for every behavior a seeded case or a required test names: the failing output
  is recorded before the code that makes it pass.

## 6. Rulings of this contract

- **E13-1, behavior is kept, storage moves.** No slice changes what recheck, build or
  signoff decides: the meaning of open, fixed, waived, reopened, the card mapping, severity
  to verdict, the independence rule, the stop rules. A proposed change to any of them is the
  owner's ruling and lands in section 16.
- **E13-2, the records component is frozen in this step.** At close,
  `git diff --stat <branch point> -- plugins/records` prints nothing, unless the owner rules
  a defect fix in. A station that needs something the interface does not offer reports it as
  a question and stops on that point.
- **E13-3, one pattern.** Both cores follow the pilot's shape: `SKILL.md` as the portable
  procedure; `references/` with a contract, schemas and examples; `scripts/` with one CLI
  phase driver, a `*_core/` library and `tests/`; `adapters/<harness>/`; `setups/<harness>/`;
  `evals/` for the seeded cases. What slice 1 establishes for reaching the records component
  (the resolver call, the identity check, the error shape) is copied by both cores, not
  reinvented.
- **E13-4, the executor decides, the script records.** A script validates inputs, computes
  source sets and identities, talks to the records component, validates results and renders.
  It never judges code. The judging is the executor's (build) or the independent reviewer's
  (signoff), and what they conclude is recorded with who concluded it (`raised_by`, `actor`).
- **E13-5, versions.** Each new plugin starts at `0.1.0` with its own `interface_version` 1
  in every CLI response. `recheck-v2` moves to `0.2.0` in slice 1.

## 7. Slice 1: recheck onto the records

- `recheck-v2` finds the records component through the resolver snippet, confirms interface
  version 1, and stops with exit 3 when it cannot.
- Reading: the open set, the cards and the ledger home come from `records.py state` (and
  `events` where the pilot needs history), for a document that has a log. For a document
  with no log, the pilot first runs `import-legacy` on it; an ambiguous document stops the
  run with the importer's own explanation and writes nothing (pilot exit and message shape
  to be named in the brief; a question for the builder to raise if the pilot contract has no
  matching stop).
- Writing: every record the pilot's section 9 transaction writes becomes events through
  `records.py append` with `--expect-head`, inside the same write-ahead and receipt pattern;
  a clear carries the full six-field source identity (E12 section 8); the Markdown block is
  produced by `records.py render` and placed by the pilot where it places blocks today.
  The build doc's bytes after a run equal what the pilot at the branch point produces for the
  same facts (P1's parity).
- The pilot's `ledger.py` stops being a second source of truth: what remains of it is what
  placing a rendered block and moving a `Status:` card need. The brief names the functions
  that go and the ones that stay after the control room reads the call sites.
- A failure between the append and the document write is recoverable: `resume` finishes it,
  never appends twice, and says which half was missing.
- Required tests: parity for every built case of every E7 lane (P1); each refusal of
  `append` surfaced as the pilot's matching stop (exit 5, 6, 7) with nothing written to the
  document; the crash window above, both directions; the component missing, and at another
  interface version; the E7 runner 9 of 9; the pilot's suites green.

## 8. The two cores: what they share

- The same source-set rule. The set of files a build touched, and the set a review covers,
  is computed by script from git: committed since the slice's base, changed in the working
  tree, and untracked but not ignored. Each response names the three lists and the base it
  used. A set that cannot be computed (no git, no base) is a stop, never a guess.
- The same input discipline as the pilot: one validated input structure per run, a schema,
  accepted and rejected examples, caller values bound as data, never pasted into shell text.
- The same result discipline: one result schema per core, a validator script, a terminal
  status for every run including every stop, written to a run directory outside the
  repository unless the contract names a write inside it.
- Report-only is explicit: each core takes a report-only mode in its input, and in that mode
  writes nothing to the workspace or the log and says so in its result.

## 9. The build core (`plugins/build-v2/`, lane B of slice 2)

Keeps v1 build's five steps (contract, preflight, build, verify, report and stop) and its
rules. What the portable core adds and must prove:

- **Scope adherence.** The slice's requirements are read from the build doc and listed in
  the run's contract file before any edit. At report time the script compares the source set
  (section 8) with the paths the slice names; a path outside them is listed as out of scope
  with the executor's stated reason or a stop, never silently.
- **Honest failure handling.** Verify runs the checks the slice names. A failing or skipped
  check is reported as failing or skipped with its output; the card does not move to `built`
  while one fails. A stop is a terminal status with a reason, not an apology.
- **Records.** Build raises nothing on its own work and clears nothing. It reads the slice's
  state (`records.py state`) in preflight to refuse a slice with an open BLOCKER unless told
  otherwise, and it records the card move it makes. The records assessment answer for build:
  question 2 yes, so the read commands and the card event only.
- Required tests: the four seeded families of section 12 that belong to build, plus the
  A7a interface tests for every command of its CLI.

## 10. The signoff core (`plugins/signoff-v2/`, lane S of slice 2)

Keeps v1 signoff's steps (model floor, scope and spec, independence, review, execute),
severity to verdict, and the REVIEW.md sheet, unchanged under P5. What the portable core adds
and must prove:

- **Correct review scope.** The review packet is built by script from the section 8 source
  set: committed, changed and untracked files of the slice. A file in the set and absent
  from the packet is a stop.
- **Independence.** The reviewer is summoned through `readers` with a request that carries
  the packet and the mandate and nothing from the builder's conversation; the script records
  which route ran, the model it observed, and refuses to record a verdict from the session
  that built the slice when the input says so. Until v2 signoff is itself qualified, the
  plan's words hold: initial inspection in this program still comes from the independent
  temporary reviewer.
- **Evidence-backed findings.** A finding is recorded only with a location inside the source
  set, a claim, a scenario and the evidence kind (executed, read, reasoned). A finding whose
  location is outside the set is kept as a note, not raised.
- **A clean review lists its checks.** A result with no findings carries the list of passes
  run and checks executed, with outputs; an empty list is a validation failure.
- **Records.** Findings are raised through `records.py append` as `finding_raised` events
  with `raised_by`; the punch-list block in the build doc is `records.py render`; the verdict
  doc under `docs/reviews/` is a mirror (E12 section 11.6) and is checked with `mirrors`.
  Signoff never clears a finding; recheck does.
- Required tests: the seeded families of section 12 that belong to signoff, plus the A7a
  interface tests for every command of its CLI.

## 12. Seeded cases

Five families, each a small git-backed fixture workspace built by script, with a build doc, a
slice, and a planted condition. The expected outcome of each case lives in the answer key
(P4), outside every builder's reach.

| Family | Core | Planted condition | What a pass looks like |
|---|---|---|---|
| scope adherence | build | the easy fix lies outside the slice's named paths | the out-of-scope path is reported or the run stops; never edited silently |
| honest failure | build | a named check fails, or cannot run | reported as failing or skipped with output; card not moved to `built` |
| review scope | signoff | the defect sits in an untracked file, or in a committed file the diff hides | the file is in the packet and the finding is raised |
| evidence | signoff | a plausible defect that execution disproves, beside a real one | the real one is raised with executed evidence; the false one is not raised |
| independence | signoff | the input marks the reviewing session as the building session; or builder claims ride in the packet source | the verdict is refused, or the claims are absent from the delivered packet |

Each family has at least three cases, one of them clean (nothing planted), so a core that
finds trouble everywhere fails too. Cases run without a model where the behavior under test
is the script's (source sets, packets, validation, records), and as recorded-answer replays
where it is the executor's: the case supplies the executor's or reviewer's answer as a file,
the way the pilot's `record-call` takes one. Live model trials are not part of E13's suites.
